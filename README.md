# BreakLab - 서비스 장애 실험실

서비스 사이의 실제 HTTP 통신에 지연이나 연결 차단을 넣고, 요청, 타임아웃, 재시도, 실패, 복구를 눈으로 확인하는 로컬 도구입니다.

## 실행

Docker 없이 실행 (Go, Node 필요):

    scripts/run-local.sh

Docker Compose로 실행:

    cp .env.example .env     # 토큰 값을 채운다
    docker compose up --build

둘 다 http://127.0.0.1:7700 에서 엽니다. 인증이 없으므로 외부에 공개하지 말고, 별도 서버에서는 SSH 터널로 접속하세요.

화면 개발: `scripts/run-local.sh`를 켠 상태에서 `cd web && npm run dev` 후 http://127.0.0.1:7780

## 사용 순서

1. 오른쪽에서 실험 조건을 정하고 **실험 시작**
2. **요청 1회** 또는 **반복 요청**으로 실제 요청 전송
3. A와 B 사이 연결선을 눌러 **장애 적용**
4. 아래 표에서 요청을 골라 타임라인 확인, **경로 다시 보기**
5. **장애 제거** 후 다시 요청해 복구 확인
6. **실험 종료** 후 조건을 바꿔 다시 실행하고 **실행 이력과 비교**에서 두 실행을 비교

**비상 중지**는 진행 중 요청을 취소하고 장애를 모두 제거한 뒤 프록시의 실제 상태를 읽어 확인합니다.
**화면 갱신 일시 정지**는 화면만 멈추며 요청은 계속됩니다.

## 구조

실험 트래픽: 요청 발생기(labd) → Service A → Toxiproxy → Service B

관리와 관측: 브라우저 ↔ labd(7700), 서비스 → labd(7701, OTLP/HTTP), labd → Toxiproxy 제어 API(8474)

| 위치 | 역할 |
|-|-|
| server/cmd/labd | 관리 서버 |
| server/cmd/service-a, service-b | 실험용 서비스 |
| server/internal/lab | 실행, 요청 발생, 장애 수명 주기, 관측 판정 |
| server/internal/proxyctl | Toxiproxy 제어와 정리 확인 |
| web | React 화면 |

## 화면 값의 의미

| 표시 | 근거 |
|-|-|
| 결과, 소요 시간 | 호출한 쪽이 기록한 span |
| 프록시 경유 확인 | A가 연결한 주소가 프록시이고, B가 본 상대 주소가 A의 주소와 다름 |
| 프록시 우회 감지 | A가 프록시가 아닌 주소에 연결했거나 B가 A를 직접 봄. 장애가 적용됐다고 표시하지 않음 |
| 관측 대기 / 일부 누락 / 판단 불가 | 아직 오지 않음 / 와야 할 span이 오지 않음 / 도달 여부를 알 근거가 없음 |
| 서비스 응답과 관측 수신 | 서로 다른 경로로 따로 확인 |
| 장애 적용, 제거 시각 | Toxiproxy 상태를 다시 읽어 확인한 시각 |

## 알려진 한계

- 관측 단위는 HTTP 요청과 호출 시도입니다. TCP 패킷은 보지 않습니다.
- 지연은 Toxiproxy가 TCP 데이터에 적용합니다. 연결 수립 자체는 늦어지지 않습니다.
- A와 B는 시도마다 새 연결을 맺습니다. net/http의 숨은 재시도를 막아 시도 횟수를 정확히 세기 위해서입니다.
- labd가 강제 종료되면 다시 시작할 때까지 장애가 남을 수 있습니다. 시작할 때 자동으로 정리하고 이력에 남깁니다.
- 서비스가 서로 다른 장비에 있으면 시계 차이로 구간 시간이 어긋날 수 있습니다.
